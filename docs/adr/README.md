# Architecture Decision Records (ADRs)

This directory contains Architecture Decision Records for Ontolith, documenting significant design decisions and their rationale.

## Format

We use the [MADR](https://adr.github.io/madr/) (Markdown Any Decision Records) format.

WHEN EXISTS(...)` — make SPEC §17's "MUST NOT be mutable" a store-level guarantee for SQLite, not just a port-surface convention — raises `sqlite3.IntegrityError`, the same class ADR-0011's own DB-layer constraints already use. The third trigger closes `INSERT OR REPLACE`, whose implicit conflict-row delete only trips a plain `BEFORE DELETE` trigger when `PRAGMA recursive_triggers` is ON (SQLite defaults it OFF, round-1 review finding) — and since that pragma is per-*connection*, not persisted in the file, a second raw connection to the same database revived the bypass regardless (round-2 finding), closed durably by making the guard schema state instead of connection state. DuckDB (verified against 1.5.4) has no `CREATE TRIGGER` support and no connection-level access-restriction mechanism to work around it — documented as a currently-unfixable asymmetry, mirroring ADR-0032's own precedent, with `conformance/test_audit_table_immutability.py` pinning both the SQLite guarantee (including from a second connection) and the DuckDB gap as executable tests rather than only a comment). **Update (KI-071/KI-075)**: `Contradiction.metadata["rationale_history"]` (KI-071's fix for `flag_contradiction()` silently dropping `rationale` on its "extend" branch) deliberately took the opposite mutability guarantee from this ADR's own audit tables — a plain, wholesale-replaceable `metadata` blob, not a trigger-protected event table — since it's an optional, free-text explanation on a review-routed dispute, not itself part of any capability or governance decision. - [ADR-0048](ADR-0048-include-flagged-history-query-opt-ins.md) — **`.include_flagged()` / `.include_history()` Are Match-Set Wideners, Not Result-Shape Changes** (KI-081: both SPEC §11.2 opt-ins now exist on `QueryBuilder` — they widen *which assertion statuses a `.where()` filter may match against*, nothing more. Default = `active`; `.include_flagged()` adds `flagged`; `.include_history()` adds `superseded` + `retracted`; the two are independent. `.all()`/`.first()`/`.count()` keep their return types — no per-entity timeline is attached (that's still `kb.assertions(status=None)` / `kb.provenance()`). No effect on a query with neither a `.where()` filter nor (since KI-093) a confidence/trust floor — nothing to widen. `.include_history()` is a no-op under `.as_of()` for `superseded` — but not for `retracted`, per ADR-0049/KI-095's Update below; `.include_flagged()` is unconditionally not a no-op there (it has applied on the `as_of` path since before this ADR, now including the confidence/trust floors too). `StorageBackend.entities_where()` gains `include_history: bool`; the current-state branch's hard-coded `status = 'active'` becomes a parameter-bound `status IN (…)` on both adapters. **Update (KI-093)**: `entities_meeting_confidence()`/`entities_meeting_trust()` gained the identical parameters and widening on both their current-state and `as_of` branches — the wideners now genuinely compose with `.min_confidence()`/`.trust_at_least()`, closing a gap where a no-op floor chained after `.include_history()` silently re-narrowed the result to active-only, and making `.include_flagged()` observable even on a `.where()`-less query once a confidence/trust floor is present. **Update (KI-094)**: REST's `/query`, GraphQL's `Query.query`, and MCP's `ontolith.query` all gained `include_flagged`/`include_history` parameters forwarding to the same two opt-ins — previously reachable only from the Python SDK. **Update (KI-095, ADR-0049)**: `.include_history()` is no longer unconditionally a no-op under `.as_of()` — it now opts out of ADR-0049's retraction-aware exclusion, the first thing it does on that path.)
- [ADR-0049](ADR-0049-retraction-aware-as-of.md) — **`as_of()` Excludes a Retraction Once Its Own Assertion-Time Has Passed** (KI-095: a retracted assertion whose `valid_to` was never narrowed (an explicit future end date, or one already closed by a different prior event) kept matching `as_of(t)` for any `t` its stale window still covered, unmet SPEC §11.2 "excluded by default." Fix is read-side only: `entities_where()`/`entities_meeting_confidence()`/`entities_meeting_trust()`'s `as_of_time` branch (all three, matching KI-093's precedent that they move together) gains a second, independent exclusion — a `retracted` assertion is invisible once its own `assertion_event` retraction timestamp is `<= t` — reusing the timestamp KI-051's write path already records exactly once per assertion, no new column, no data loss, `valid_to` itself untouched. `.include_history()` becomes the opt-out, the first thing it has ever done under `.as_of()`. Rejected: closing `valid_to` to the retraction instant at write time (conflates assertion-time correction with valid-time fact, and is a genuine irreversible data loss since `AssertionEvent` never snapshots field values); a dedicated `retracted_at` column (duplicates what `assertion_event` already tracks). **Update (KI-098)**: `StorageBackend.assertions()` — left with no opt-out of its own when this ADR shipped — gained an `include_history` parameter mirroring `include_flagged`'s existing shape on the same method.)
- [ADR-0050](ADR-0050-time-varying-many-supersedes-hint.md) — **An Explicit `supersedes` Hint Resolves `time_varying` + `cardinality="many"` Ambiguity** (KI-080: ADR-0017 deliberately never extended cardinality-aware routing to `time_varying` properties, reasoning that an overlapping differing value is always a genuine supersession there — true for `cardinality="single"`, but not for `"many"`, where window overlap plus a differing value can't tell "replace my current value" from "a new, additional concurrent value" apart. `_route_time_varying` now consults `cardinality`: a `many`-cardinality overlapping differing value coexists by default (mirrors `_route_static`'s own "many" branch), unless a new `supersedes: str | None` parameter on `assert_literal`/`assert_ref`/`propose`/`propose_ref` names the one specific existing assertion to replace instead — every other overlapping-differing value stays untouched. Rejected: always-coexist with no new parameter (can't express a correction without a separate `retract()` round trip); inferring replacement from a "closest match" heuristic (SPEC §10 has no inference step); a separate `resolve_supersession()` call decoupled from the write (reopens a window where both values look simultaneously active with no signal a replacement is imminent). REST/GraphQL/MCP/CLI parity deliberately out of scope, filed as its own follow-up (KI-099). **Update (KI-099)**: `supersedes` now reaches every write-shaped interface — REST's `WriteAssertionIn`/`ProposeIn`, GraphQL's `ProposeInput`, MCP's `propose` tool, and the CLI's `ontolith assert` (`--supersedes`) — each forwarding straight through to `Ontology`, which does all real validation.)
- [ADR-0051](ADR-0051-plugin-process-isolation.md) — **Plugin Process Isolation** (KI-014's still-open half: ADR-0015 gave plugins a governance-correctness boundary but left `capabilities.network`/`.filesystem` declared, not enforced, and explicitly named "Python has no true encapsulation" as the deeper reason — closing it needed real process/wasm isolation, deliberately deferred until real plugins existed to run in it. Four reference plugins now ship, so this ADR builds it: `PluginRegistry.register(isolate=True)` (the new default) runs a plugin's one protocol entrypoint in a freshly spawned child process, with its `kb` view and any other live argument (e.g. an `io.StringIO` export target) proxied back to the parent over one IPC pipe — closing the "no true encapsulation" gap structurally, on every platform, since only picklable messages cross the boundary at all. Network/filesystem denial is enforced at the OS syscall level on Linux via seccomp (`ERRNO(EPERM)`, not `KILL_PROCESS`, so a denied syscall surfaces as an ordinary caught exception); macOS/Windows get no OS-level enforcement in this pass, honestly documented rather than approximated with an unverifiable mechanism. `.query()`/`.as_of()` are unsupported inside an isolated call (no shipped plugin needs them; filed as **KI-101**). Rejected: a long-lived worker process reused across calls (no plugin needs cross-call state, and it would let one bad call taint every later one); WASM-based plugin execution (a fundamentally different authoring model than this project's entry-point-based Python plugins, phased separately per the Implementation Plan); in-process Python-level restriction via monkeypatching `socket`/`open` (trivially defeated by deliberately malicious code, the same reason ADR-0015 rejected a `StorageBackend` wrapper for the storage half). `isolate=False` is the documented escape hatch, restoring exactly the pre-ADR-0051 behavior. **Update**: five review rounds — round 1 (architecture + a dedicated security review) found the process boundary itself was bypassable as first built, two CRITICALs — the dispatch loop unpickled the child's own bytes with plain `pickle.loads()` (reproduced: arbitrary code execution in the parent) and invoked any method name the child asked for on the real, unproxied view with no allow-list (reproduced: privilege escalation via `__setattr__`, no pickle needed) — both fixed (a restricted unpickler with an explicit exception-class allowlist; an explicit method-name allow-list before dispatch) and re-verified by reproducing both attacks against the fixed code; rounds 2-4 each re-verified the CRITICALs and closed one real regression the prior round's own fix had introduced in the same message-handling code; round 5 found no further code-level issues. See the ADR's own Update section for the full record.)
- [ADR-0052](ADR-0052-storage-format-migrations.md) — **On-Disk Storage-Format Migrations** (SPEC §15: `format_version` didn't exist anywhere, and the backend's own DDL evolution — KI-060's `principal_credential.issued_by`/`.revoked_by`, KI-078's `proposal.reviewers` — was handled by an ad hoc `PRAGMA table_info` check + idempotent `ALTER TABLE` at the top of `_create_schema()`, silently, on every connect, satisfying none of SPEC §15's three requirements (a tracked format_version, a dry-run mode, declared reversibility). New `format_version` single-row table, tracked independently per backend (`store/sqlite/migrations.py`, `store/duckdb/migrations.py` — no cross-backend `StorageBackend` port method, since the whole point is to work on a file a normal backend constructor would refuse to build). `SQLiteBackend`/`DuckDBBackend` now refuse (`SchemaError`) to open an existing file below `CURRENT_FORMAT_VERSION` rather than silently upgrading it; `migrate_file(path, *, dry_run=False)` is the explicit, standalone action that actually applies pending migrations (or, dry-run, only reports them) — exposed as `ontolith db status`/`ontolith db migrate [--dry-run]` (SQLite only, matching `Ontology.connect()`'s own scope). Both historical migrations are formalized as the first two registered entries (v2, v3) and declared `reversible=True`; DuckDB's v2 reversal needs to drop and recreate `idx_principal_credential_principal` around the `DROP COLUMN` calls — DuckDB (pinned `1.5.4`, verified directly) refuses `ALTER TABLE ... DROP COLUMN` outright on any table with a secondary index, even on an unrelated column. Rejected: keeping the old silent-auto-migrate-on-connect behavior (defeats SPEC §15's dry-run implication); a `StorageBackend.migrate()` port method (the scenario needing this is exactly the one where a normal backend object can't be constructed); folding this into `ontolith schema migrate` (a different, domain-schema-scoped mechanism per ADR-0034). Data migration/backfill for a renamed/retyped *domain* predicate against already-stored assertions — ADR-0034's own "scope (b)" — remains a distinct, still-open problem this ADR does not solve.)
- [ADR-0053](ADR-0053-resolution-keeps-corroborating-members.md) — **Contradiction Resolution Keeps Members That Corroborate the Winner** (SPEC §10.4's pseudocode retracted every member except the chosen winner, discarding a second source that agreed with the winning value — contradicting §10.1's "corroboration: keep both". Proposed: resolve by winning *value* — every non-terminal member equal to the winner's `(value_kind, value)` stays/becomes `active`, differing members are retracted, retracted/superseded members stay terminal (ADR-0031). Default behavior, no new parameter; kept/retracted members are already recorded as per-member assertion events, so no storage migration. Equality is routing's own exact comparison, not canonicalized. Behavior change, flagged breaking in the CHANGELOG.)

## Decision Process

1. **Propose** — Create ADR in draft status with context and options
2. **Discuss** — Review in team/community (via PR or RFC)
3. **Decide** — Update status to "Accepted" or "Rejected"
4. **Implement** — Reference ADR in implementation PRs
5. **Supersede** — If decision changes, create new ADR and mark old one superseded

## Status Values

- **Proposed** — Under discussion
- **Accepted** — Decision made and active
- **Rejected** — Decision considered but not adopted
- **Deprecated** — Previously accepted, now superseded
- **Superseded by ADR-XXXX** — Replaced by a newer decision

## Adding New ADRs

When making significant architectural decisions:

1. Copy the MADR template
2. Number sequentially (ADR-0009, ADR-0010, ...)
3. Use descriptive filename: `ADR-XXXX-short-title.md`
4. Fill in: Context, Decision, Rationale, Consequences, Alternatives
5. Reference related SPEC sections, PRD requirements, and other ADRs
6. Add to this index
7. Create PR for review
